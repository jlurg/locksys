## Purpose and scope

This document defines the coding rules for all authored source code in the repository:

- C for the DCU firmware (`firmware/dcu/`) and the shared libraries (`libs/`), under MISRA C:2012.
- C for the CGW firmware (`firmware/cgw/`), under a MISRA-inspired subset.
- Dart for the APP (`app/`).
- Python for the HIL framework (`hil/`) and repository tools (`tools/`).
- PowerShell, shell, YAML and workflow files.

Vendored code (`third_party/`) and generated code are exempt from formatting and naming rules; their handling is defined in the sections on generated and vendored code.

## Rules for all languages

- All identifiers, comments, messages and documentation are in English.
- Authored source files start with the licence header defined below.
- No secrets, keys, passphrases, pairing URIs or personal e-mail addresses in code, test data, logs or comments.
- No commented-out code. Removed code lives in the git history.
- Work markers reference an issue: `TODO(#123): <action>`. Markers without an issue are not merged.
- No AI attribution of any kind; see [AI policy](ai_policy.md).

## Comment rules

Comments in this repository are those of a professional product code base. They document contracts and non-obvious intent. They do not teach.

### Required comments

- **Public APIs** carry Doxygen comments. A public API is every declaration in a module header that other modules include (`<module>.h`, `libs/*/include/`), every CGW port header (`*_port.h`) and every exported Dart and Python API.
- **C and C++ Doxygen** uses the `@` command form:
  - file header: `@file` and `@brief`;
  - functions: `@brief`, `@param[in]`, `@param[out]` or `@param[in,out]` for every parameter, `@return` or `@retval` for every non-void function, and `@pre`, `@post`, `@note` or `@warning` when they add a constraint (call context, timing, reentrancy, units);
  - types, enumerators, macros and constants: `@brief`, or a trailing `/**< ... */` comment.
- **Intent comments** are brief and appear only where the reason for the code is not obvious from the code itself: an ordering constraint, a hardware limitation, a timing assumption, a deliberate deviation from the expected pattern.
- **Reference comments** link code to its source of truth:

| Reference | Form |
| --- | --- |
| Requirement implemented | `/* @satisfies SWR-DCU-012 */` directly above the implementing function or block |
| Requirement verified (C test) | `/* @verifies SWR-DCU-012 */` directly above the test function |
| Requirement verified (Python test) | `@pytest.mark.verifies("SYS-021")` on the test function |
| Requirement verified (Dart test) | `// @verifies SWR-APP-012` on its own line directly above the test |
| Errata | `/* ES096 §2.5.1: regular conversions only on ADC12_IN0. */` |
| Reference manual or datasheet | `/* RM0008 §9.3: SWJ_CFG is write-only; MAPR is written once. */` |
| MISRA deviation | `/*cstat !MISRAC2012-Rule-11.4 : DEV-DCU-003 CMSIS peripheral base address*/` |

Trace tags carry one full requirement ID each. Several IDs are written as several tags. Tags never abbreviate an ID.

### Forbidden comment content

- Tutorial or educational prose, for example explanations of how CAN arbitration, PWM, an H-bridge or a C language feature works in general.
- Comments that restate the code.
- Narrative, conversational or first-person text, questions and notes to self.
- Author names, dates and change histories; the git history holds them.
- Decorative banners and separator lines.
- Non-English text, emoji and AI attribution.

### Example

```c
/* SPDX-License-Identifier: Apache-2.0 */
/* Copyright (c) 2026 jlurg */

/**
 * @file win_pos.h
 * @brief Window motor speed, direction and relative position from the encoder.
 */

#ifndef WIN_POS_H
#define WIN_POS_H

#include <stdint.h>

/**
 * @brief Samples the encoder counter and updates speed and relative position.
 *
 * @pre WinPos_Init() has completed.
 * @note Called from the 10 ms task only; not reentrant.
 */
void WinPos_Main10ms(void);

/**
 * @brief Returns the encoder counts measured in the last 10 ms period.
 *
 * @return Signed count difference; positive values mean the UP direction.
 */
int16_t WinPos_GetDelta10ms(void);

#endif /* WIN_POS_H */
```

## C: DCU firmware and shared libraries

### Language and compliance

- ISO C11 as accepted by IAR EWARM with language extensions disabled, and by GCC with `-std=c11` for host tests and the shadow build. Compiler extensions (`__no_init`, intrinsics, section placement) are used only through `ls_compiler.h`.
- MISRA C:2012 including Amendments 1 to 4, enforced as defined in the [Guideline Enforcement Plan](misra/gep.md). IAR C-STAT is the authoritative checker. The gate is zero unsuppressed findings.
- Deviations follow the [deviation process](misra/deviation_process.md) and are recorded in [deviations.yaml](misra/deviations.yaml).

### Design rules

| Rule | Detail |
| --- | --- |
| No dynamic memory | No `malloc`, `free` or heap. Checked by C-STAT and the linker map check. |
| No recursion | Direct or indirect. Checked by C-STAT and the linker stack analysis. |
| No function pointers | Bindings are resolved statically in `*_cfg.c`. Visual State code is generated without function pointers ([ADR 0013](../adr/0013-iar-visual-state-for-dcu-state-machines.md)). |
| No floating point | Integer and fixed-point arithmetic only. Introducing floating point requires an ADR. |
| Fixed-width types | `<stdint.h>` and `<stdbool.h>` types; no plain `int`, `char` or `long` for data. |
| Bounded loops | Every loop has a compile-time bound or a checked iteration or time limit; hardware polling loops always have a timeout. |
| Control flow | One exit point per function; no `goto`; every `switch` has a `default`; no fall-through. |
| Return values | Every return value is used or explicitly discarded with `(void)`. |
| Linkage and scope | File-scope objects and functions are `static`; `const` wherever possible; no global variables shared between modules except through the RTE. |
| Layering | MCAL, ECUAL, Services, RTE, SWC; dependencies point downward only. Registers are accessed only in `platform`, `mcal` and `startup`. Checked by `tools/arch/check_layers.py`. |
| Interrupts | ISRs are short and hand data to tasks through single-producer single-consumer buffers or reflex latches. Data shared with ISRs is accessed in critical sections or through single-writer structures. State machine engines are never called from an ISR. |
| Configuration | Tables in `*_cfg.c`, checked with static assertions. |
| Safe defaults | Enumeration value 0 is the safe value; outputs are de-energised by default. |
| Fault injection | `Fi_` code is compiled into DEV and HIL builds only; release images contain no `Fi_` symbols (checked in CI). |
| Errata | Workarounds cite ES096 Rev 15 section numbers. |

### Visual State generated code

- The WinCtrl, DoorCtrl and ModeMgr engines in `firmware/dcu/gen_vs/{release,debug}/` are generated by IAR Visual State with the committed option files in `firmware/dcu/model/visualstate/options/`, only through `firmware/dcu/scripts/vs/Invoke-VsGenerate.ps1`. They are committed and never edited.
- Models have no event parameters. Each translation unit includes at most one generated system header. An engine is called only from its own SWC adapter in the 10 ms task.
- The modelling rules are in the [Visual State modelling guide](../04_software/dcu/visual_state_guide.md).

### Complexity limits

Measured with lizard on authored C in `firmware/dcu/src/`, `firmware/dcu/cfg/`, `libs/*/src/`, `firmware/cgw/components/` and `firmware/cgw/main/`. Generated, vendored and test code is not measured.

| Metric | Limit | Enforcement |
| --- | --- | --- |
| Cyclomatic complexity per function | 10; 11 to 15 requires a justification in the PR | Warning above 10, failure above 15 |
| Parameters per function | 5 | Failure above 5 |
| Lines of code per function (NLOC) | 50 | Warning above 50 |
| Nesting depth | 4 | Warning above 4 |

The executable form of these limits, and of the coverage thresholds per scope, is `tools/ci/quality_gates.yaml`. Coverage targets are defined in the [verification strategy](../07_verification/verification_strategy.md).

## C: CGW firmware

The CGW runs ESP-IDF and FreeRTOS, whose own code is not MISRA-compliant. CGW components (`cgw_*`) follow this MISRA-inspired subset:

| Rule (MISRA C:2012 reference) | Enforcement |
| --- | --- |
| No dynamic allocation in `cgw_*` after initialisation (Dir 4.12, Rule 21.3); ESP-IDF stacks that use the heap are monitored | Host link test that wraps `malloc`; review |
| No recursion (Rule 17.2); bounded loops; no blocking calls in core components | Review; static analysis |
| Fixed-width types (Dir 4.6); no floating point in core components | `-Wdouble-promotion`; review |
| Explicit, checked conversions (Rules 10.x) | `-Wconversion -Wsign-conversion` on core components |
| Every `switch` has a `default`; no implicit fall-through (Rules 16.3, 16.4) | `-Wswitch-enum -Wimplicit-fallthrough` |
| All return values checked (Rule 17.7, Dir 4.7); `ESP_ERROR_CHECK` only during initialisation | `warn_unused_result` on project APIs; review |
| Internal linkage; no shared global variables (Rules 8.7, 8.8); const correctness (Rule 8.13); cross-task state limited to the documented handoffs | `-Wmissing-prototypes`; review |
| Wrap-safe `uint32_t` millisecond arithmetic; secrets zeroised after use and never logged | Unit tests; HIL log scan |

- Warning flags for all components: `-Werror -Wall -Wextra -Wshadow -Wundef -Wcast-align -Wstrict-prototypes -Wmissing-prototypes -Wformat=2 -Wvla -Wnull-dereference`. Core components add `-Wconversion -Wsign-conversion`.
- cppcheck and host tests with AddressSanitizer and UndefinedBehaviorSanitizer cover the portable core.
- Deviations from this subset use `DEV-CGW-nnn` records in the deviation register.
- Naming: components `cgw_<area>`, functions `cgw_<area>_<verb>()`, types `<name>_t`, ports `*_port.h`, ESP-IDF adapters `*_esp.c`, host-portable adapters `*_<backend>.c`.

## Dart: APP

- Effective Dart. The lint set is `very_good_analysis` 11.0.0, configured in `app/analysis_options.yaml`.
- `flutter analyze --fatal-infos` reports no issues and `dart format` produces no changes.
- Public classes, members and top-level declarations carry `///` documentation.
- File names `snake_case.dart`; feature code under `lib/features/<feature>/{data,domain,presentation}`; tests `<name>_test.dart`.
- Generated protocol code (`app/packages/locksys_protocol/lib/src/gen/`) is not edited and is excluded from analysis.
- Architecture rules (layers, state management, dependency composition) are defined in the [APP architecture](../04_software/app/architecture.md).

## Python: HIL and tools

- Python 3.13 in the uv workspace; dependencies are locked in `uv.lock` and installed with `uv sync --locked`.
- PEP 8 enforced by ruff with the rule families E, F, W, I, B, UP, SIM, PL, S, PT and RUF; formatting by `ruff format`. The root `pyproject.toml` holds the authoritative configuration.
- mypy in strict mode; all functions carry type annotations.
- Tests are pytest modules named `test_<topic>.py`. Hardware-free tests run in CI.
- Subprocesses are started with argument lists, never through a shell string.
- Secrets are never logged. HIL secrets are wrapped in a type whose representation is redacted, and pytest never runs with `--showlocals`.

## PowerShell

- PowerShell 7. Scripts start with `Set-StrictMode -Version Latest` and `$ErrorActionPreference = 'Stop'`.
- Script and function names use approved verbs (`Verb-Noun`), for example `Invoke-DcuBuild.ps1`.
- Parameters are declared in a `param()` block with `[CmdletBinding()]`; no aliases in scripts; explicit exit codes.
- Line endings are CRLF, as defined in `.gitattributes`.

## Shell

- Bash with `#!/usr/bin/env bash` and `set -euo pipefail`.
- shellcheck reports no findings. All expansions are quoted.
- Scripts run on macOS and on the Ubuntu CI runners.

## YAML, JSON and workflows

- Two-space indentation; files are validated by the pre-commit hooks.
- Workflows pass actionlint and zizmor. Untrusted values (PR titles and bodies, branch names) reach scripts only through `env:`, never through expression interpolation inside `run:`.

## Formatting

| Content | Tool and configuration |
| --- | --- |
| All files | `.editorconfig`: UTF-8, LF line endings (CRLF where `.gitattributes` requires it), final newline, no trailing whitespace |
| Authored C | clang-format with the repository `.clang-format` |
| Dart | `dart format` |
| Python | `ruff format` |
| Markdown | markdownlint-cli2 with `.markdownlint-cli2.yaml` |
| Spelling | typos with `typos.toml` |

Formatting is applied by the pre-commit hooks and checked again by the `lint` job in CI.

## Generated and vendored code

- Generated code starts with its `DO NOT EDIT` line, is committed, and is regenerated only with `uv run tools/codegen/regen.py` (and the Visual State generation script for `gen_vs/`). `uv run tools/codegen/regen.py --check` fails on any drift.
- Generated code is marked `linguist-generated` in `.gitattributes` and is excluded from formatting and complexity measurement. It is still analysed by C-STAT as defined in the [Guideline Enforcement Plan](misra/gep.md).
- Vendored code in `third_party/` keeps its upstream form and notices and is not modified. Its origin, version and SHA-256 are listed in `third_party/README.md`.

## Rationale

- MISRA C:2012 with C-STAT as authoritative checker gives the DCU a defined, auditable rule set; the design rules (no heap, recursion, function pointers or floating point) keep the stack and timing analysable.
- The CGW cannot be fully MISRA-compliant on top of ESP-IDF; the subset keeps the portable core analysable and testable on the host.
- Professional comment rules keep the code base reviewable: contracts in Doxygen, intent where needed, and explicit links to requirements, errata and deviations.
