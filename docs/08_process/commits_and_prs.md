## Purpose and scope

This document defines the commit message format, the pull request (PR) rules, size guidance, the review checklist and the Definition of Ready (DoR) and Definition of Done (DoD) per work item type. It applies to every commit and PR in `jlurg/locksys`, including those prepared with tool assistance. Branch names and merge methods are defined in [Branching model](branching.md).

## Commit messages

Commit messages follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/).

```text
<type>(<scope>[,<scope>...])[!]: <subject>

<body>

<footer>
```

### Types

| Type | Use |
| --- | --- |
| `feat` | New behaviour visible at a requirement or interface level |
| `fix` | Correction of a defect |
| `perf` | Timing, memory or throughput improvement without behaviour change |
| `refactor` | Code restructuring without behaviour change |
| `test` | Tests, test data, HIL test cases |
| `docs` | Documentation only |
| `build` | Build system, toolchain pins, dependencies, version bumps, release preparation |
| `ci` | Workflows, CI scripts, repository automation |
| `chore` | Maintenance not covered by the other types |
| `revert` | Revert of an earlier commit |

### Scopes

| Scope | Area |
| --- | --- |
| `dcu` | DCU firmware (`firmware/dcu/`) |
| `cgw` | CGW firmware (`firmware/cgw/`) |
| `app` | Flutter application (`app/`) |
| `hil` | HIL framework, procedures and stimulus firmware (`hil/`) |
| `can` | CAN matrix and its generated code (`interfaces/can/`) |
| `proto` | APP to CGW protocol (`interfaces/proto/`) |
| `libs` | Shared C libraries (`libs/`) |
| `docs` | Documentation (`docs/`) |
| `ci` | Workflows and CI scripts |
| `build` | Build configuration and toolchains |
| `tools` | Repository tools (`tools/`) |
| `deps` | Runtime dependency updates |
| `deps-dev` | Development dependency updates |
| `release` | Release preparation, back-merges, version files |
| `repo` | Repository-wide files and settings |

Several scopes are separated by commas without spaces, for example `feat(can,dcu): ...`.

### Subject, body and footers

- The header (type, scope and subject) is at most 72 characters and the subject 3 to 70 characters; the header uses the imperative mood, starts the subject with a lowercase letter or digit and has no trailing period. The maximum lengths do not apply to PR titles generated by Dependabot (head branch `dependabot/**`), which are outside the maintainer's control; the format rules still apply.
- The body states what changed and why. Lines wrap at 72 characters.
- `!` after the type or scope and a `BREAKING CHANGE:` footer are mandatory for any incompatible change, in particular an interface major version change (CAN matrix, APP protocol, UART telemetry).
- Footers:
  - `Closes #<issue>` or `Refs #<issue>` links the issue.
  - `Req: <ID>, <ID>` lists the requirement IDs the change implements or verifies, for example `Req: SWR-DCU-042, SYS-021`.
  - `Co-authored-by: <name> <email>` credits human co-authors only.
- AI attribution is forbidden in any form; see [AI policy](ai_policy.md).
- Messages are written in English.

### Signing and identity

- Every commit is signed with an SSH signing key registered on the author's GitHub account. Unsigned commits cannot be merged into protected branches.
- Commits use the author's GitHub noreply address. The repository identity is configured per clone (`git config user.name`, `git config user.email`), never changed by tools.

### Examples

```text
feat(dcu): add encoder no-motion supervision

Brake and latch NO_MOTION when the measured counts stay below the
configured fraction of the expected counts after the start grace time.

Closes #42
Req: SWR-DCU-031, SYS-042
```

```text
feat(can)!: rename WinSts_Pos to WinSts_PosPct

BREAKING CHANGE: CAN matrix 2.0; DCU and CGW must be updated together.

Refs #77
```

## Pull requests

### General rules

- One topic per PR. Every PR links an issue and lists the requirement IDs it touches.
- The PR title becomes the subject of the squash commit and must match:

  ```text
  ^(feat|fix|perf|refactor|test|docs|build|ci|chore|revert)(\([a-z-]+(,[a-z-]+)*\))?!?: [a-z0-9].{1,68}[^.]$
  ```

  Every scope must be one of the scopes above. GitHub's default revert title is edited to the `revert: ...` form.
- The PR body becomes the body of the squash commit (repository setting `squash_merge_commit_message = PR_BODY`). The checklist state in the body is therefore permanent verification evidence: tick only items that are true and mark the others "N/A" with a reason.
- Open draft PRs early to get CI feedback.
- Requirement changes are merged as a documentation PR before the implementation PR.
- Generated code is regenerated with `uv run tools/codegen/regen.py` (or the Visual State generation script) and committed in the same PR as its source change. It is never edited by hand.

### PR template

The repository PR template (`.github/PULL_REQUEST_TEMPLATE.md`) contains the following sections. Each section is completed; nothing is deleted.

| Section | Content |
| --- | --- |
| Summary | What and why, 1 to 5 lines |
| Links | Closing keyword and issue, requirement IDs, ADR if any |
| Impact | Interface change with version impact (none, minor, major); safety-relevant change; security-relevant change |
| Verification | Unit tests with `@verifies` tags and coverage; `iar-gate` result for DCU and libs; HIL evidence (mandatory for safety-relevant changes); documentation and trace updates; regenerated code |
| Hygiene | Branch name and title conform; no secrets, keys or pairing URIs; no AI attribution |

HIL evidence is pasted as a result summary, not only as a link: workflow runs and their check results are deleted after the 90-day retention period of a public repository.

Safety-relevant changes are changes to WinCtrl, DoorCtrl, ModeMgr, SafeMon, WdgM, EcuM, HBridge, WinPos, LockAct, VbatMon, TempMon, CanIf, Com and E2E, `libs/ls_e2e`, the CAN matrix, the CGW arbiter and session handling, and the APP hold-to-run control.

### `pr-policy` checks

| Check | Rule | Exemptions |
| --- | --- | --- |
| Branch name | Matches a pattern in [Branching model](branching.md) | Length limit does not apply to `dependabot/**` |
| Base and head | Allowed combination per [Branching model](branching.md) | None |
| Title | Conventional title regex, scope list, header at most 72 and subject at most 70 characters | Length limits do not apply when the head branch is `dependabot/**` |
| Linked issue | A closing keyword or `Refs #<n>` in the body | `dependabot[bot]`, `sync/*` branches, release and hotfix PRs into `main` (they reference the milestone) |
| AI attribution | No AI attribution in commit messages, author or committer identities, PR title or body | None |

### Size guidance

- Target at most 400 changed lines, excluding generated code (`gen/`, `gen_vs/`), lock files and vendored code (`third_party/`).
- PRs above 800 changed lines need a justification in the summary.
- The `size-label` job of `pr-policy.yml` applies `size/XS` (below 10 lines), `size/S` (below 100), `size/M` (below 400), `size/L` (below 800) or `size/XL`. It is best effort and not part of the required check.
- Interface changes are split: first a PR with the interface source, the regenerated code and the documentation, then one implementation PR per node.

### Review checklist

The author performs this review on every PR while the project has a single maintainer. With collaborators it becomes the reviewer checklist.

1. Requirements and acceptance criteria are met; `@satisfies` and `@verifies` tags are correct and complete.
2. MISRA and C-STAT are clean; no heap use, bounded loops, every return code checked.
3. Safety: interlocks, timeouts and safe states are unchanged, or the change is analysed in the PR with the affected safety mechanisms (`SM-nn`) referenced.
4. Security: no key material in logs, constant-time comparisons kept, inputs validated.
5. Interface changes are regenerated, versioned and implemented on both nodes.
6. Timing, CPU load and stack budgets are not degraded.
7. A bug fix comes with a test that fails without the fix.
8. Documentation, ADR and changelog impact are handled.
9. Safety-relevant PRs: the diff is read again at least 12 hours after the last change before merging.

## Definition of Ready and Definition of Done

| Item type | Ready when | Done when |
| --- | --- | --- |
| Feature | Issue form complete; requirement IDs exist with status approved; acceptance criteria stated; milestone set; `scope:MVP` or `scope:LATER` label; safety and security flags set | Code tagged `@satisfies`; unit tests tagged `@verifies` and coverage targets met; static analysis clean (C-STAT for DCU and libs, compiler and cppcheck for CGW, `flutter analyze` for APP, ruff and mypy for Python); design documents updated; trace report updated; HIL test added or updated if system behaviour changed; all required checks green |
| Bug | Reproduction steps, commit SHA or version, logs, DTCs if any | A regression test fails before the fix and passes after it; root cause stated in the PR; DTC and telemetry impact noted; hotfix decision recorded if the bug affects a release |
| Requirement change | Impact analysis covering SYS, SWR, HWR, tests, interfaces, safety and security; version impact stated | Documentation PR merged before the implementation PR; trace data updated; interface version changed where needed |
| HIL failure | Workflow run link, commit SHA, bench configuration, evidence | Classified within 2 days as product, bench, infrastructure or flaky; product failures become a bug; flaky tests are quarantined with an issue for at most 14 days |
| Documentation | Scope and target documents defined | Markdown lint passes; relative links resolve; Mermaid diagrams render on GitHub; IDs follow the conventions in the [documentation index](../README.md) |
| CI or tooling | Effect on self-hosted runners assessed | actionlint and zizmor clean; actions pinned by full commit SHA, including nested actions; no new trigger lets untrusted code reach a self-hosted job; a workflow run link shown as evidence |
| Release | Release checklist entry criteria met | Immutable release published with its evidence pack; release record completed |

## Rationale

- Conventional Commits give a machine-readable history for changelog generation (`git-cliff`) and make interface breaks explicit through `!`.
- Squash merging with `PR_TITLE` and `PR_BODY` makes the reviewed PR text the permanent commit text, so verification statements survive the 90-day retention of workflow data.
- Explicit DoR and DoD per item type keep requirement, test and evidence obligations visible to a single maintainer without a separate review role.
